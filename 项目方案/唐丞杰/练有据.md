# 练有据

> 基于训练视频与运动记录的个人训练复盘助手。

**提案状态：备选项目，尚未立项。** 本文分析产品需求、竞争差异与实现可行性，不代表相关功能已经开发，也不代表已有用户调研结论。竞品资料查阅日期：2026 年 11 月 12 日。

## 一、项目定位

练有据面向缺少持续指导、希望了解自己训练变化的普通运动者，将训练计划、组次记录、动作视频、主观感受与历史表现关联起来。用户完成训练后，可以回看某一次动作、理解可观察的变化，并为下一次训练确定关注点。

项目的核心价值是：**让“练了多少、动作怎样、是否进步、下次关注什么”能够相互解释。** 视频分析是核心能力，训练记录为分析提供上下文，历史对比让产品产生持续使用价值。

名称“练有据”表达的是每条复盘结论都尽量有可回看的训练证据。项目属于 AI＋生活、AI＋影像方向，适合以移动端完成拍摄和记录，以 Web 端完成详细复盘与教练协作。

## 二、目标用户与需求场景

| 用户 | 典型场景 | 需要解决的问题 | 预期收益 |
|---|---|---|---|
| 独自训练的健身初学者 | 根据教程练习后，不知道自己哪些地方需要调整 | 教程展示与自身动作之间缺少具体对照 | 看懂自己的动作片段，获得少量明确关注点 |
| 已有记录习惯的普通训练者 | 重量和次数在增加，但不确定动作节奏是否发生变化 | 数字记录与视频证据割裂 | 同时比较训练量与动作表现 |
| 居家运动者 | 使用手机完成自重或小器械训练 | 缺少旁人观察，拍摄和回看成本较高 | 降低记录负担，形成可持续的个人训练档案 |
| 提供课后指导的教练或校园运动社团 | 学员提交多段视频，指导意见分散在聊天记录中 | 难以定位具体动作并追踪建议是否落实 | 在同一段视频和同一条训练记录上完成反馈 |

主要需求假设：用户愿意为部分训练组录制短视频，愿意在训练后花少量时间复盘，并认为持续对比比单次泛化评价更有帮助。这些假设需要通过试用验证，不能仅由健身人数或开源项目热度推导成立。

## 三、现有方式的痛点

### 1. 训练记录难以解释动作变化

组数、次数和重量可以反映训练安排，却难以说明动作节奏、活动范围、暂停位置等变化。仅看“多做了两次”，用户可能无法判断本次表现与上次是否具有可比性。

### 2. 用户拍了视频，却没有形成复盘习惯

视频通常留在相册中，缺少动作名称、重量、组次等上下文。训练数周后，很难找到条件相近的旧视频，也很难准确对齐同一动作阶段。

### 3. 泛化反馈缺少证据和优先级

“注意稳定”“控制速度”等表述很难直接执行。用户更需要知道：哪一次、哪个阶段出现了什么可观察现象，以及下次应该先关注哪一项。

### 4. 不同拍摄条件容易制造错误比较

机位、距离、遮挡与动作变式都会影响分析。系统如果忽略这些条件，容易把拍摄变化解释为运动表现变化。

## 四、产品流程与功能结构

**建立训练安排 → 拍摄与记录 → 视频质量检查 → 动作分段与指标提取 → 证据化复盘 → 历史对比 → 设置下次关注点。**

| 模块 | 主要功能 | 在产品中的作用 |
|---|---|---|
| 训练安排与日志 | 动作、组次、重量、休息、备注及主观用力程度；沿用历史记录快速填写 | 为视频提供训练上下文，形成日常入口 |
| 拍摄辅助 | 机位示意、全身入镜检查、遮挡与清晰度提示、短视频导入 | 提高分析条件的一致性 |
| 视频分析 | 人体关键点、动作周期、重复次数、阶段时间和可观察的相对运动范围 | 提供可复核的基础事实 |
| 复盘时间线 | 点击结论跳到相应片段，叠加关键点、轨迹与阶段标记 | 帮助用户理解系统判断 |
| 历史对比 | 筛选相近动作变式与拍摄条件，按动作阶段对齐，支持并排回放 | 展示个人变化，避免仅比较体重和训练总量 |
| 下一次训练衔接 | 用户确认关注点，关联下一次训练；结合日志和个人设置提供可编辑建议 | 将分析转化为后续行动 |
| 协作与导出 | 分享选定片段、附加教练批注、导出训练周报 | 便利沟通，也支持人工纠正系统解释 |

### 一个完整使用示例

用户完成一组自重深蹲，录入次数和感受后上传侧面视频。系统检查入镜情况，将视频切分为重复动作，展示下降、底部和上升阶段的时长。用户发现后几次上升阶段明显变慢，点击提示直接回看对应片段。

系统找到条件相近的历史视频，按动作阶段对齐展示。用户可以比较节奏和身体关键点轨迹，并将“保持下降节奏一致”设为下次关注点。这里的时长变化来自计算结果；“是否因疲劳导致”只能作为待确认解释，不由视频直接认定。

## 五、与类似产品的差异

以下竞品能力依据官方公开说明归纳；差异是拟建设方向，不是未经实测的全面优越性声明。官网没有列出某项能力，也不能据此断言竞品完全不具备。

| 产品／类型 | 已公开的主要能力 | 对本项目的启发 | 练有据拟重点验证的差异 |
|---|---|---|---|
| [openGym](https://github.com/DuarteSantos8/openGym) | 训练安排、运动日志、肌群与身体数据追踪，支持移动端及自托管 | 训练记录是完整产品的基础，而非视频分析的附属页 | 将具体训练组、视频片段和历史对比连为同一条记录 |
| [Hevy](https://www.hevyapp.com/features/) | 训练记录、进步追踪、社交、媒体上传及教练协作 | 仅增加上传视频或图表，很难形成差异 | 对重复动作进行阶段对齐，反馈定位到时间段，并跟踪关注点 |
| [Fitbod](https://fitbod.me/) | 根据目标、器械及记录个性化安排力量训练 | 个性化计划已有成熟竞争，不能只把模型生成计划当创新 | 让后续建议能够引用用户实际视频中的可观察证据 |
| [Kemtai](https://kemtai.com/fitness/) | 摄像头运动追踪、实时动作反馈与评估 | 摄像头识别和动作反馈本身已有成熟实现 | 侧重训练后复盘、个人长期对比与用户／教练共同确认 |
| 通用多模态问答 | 用户可以上传运动图像或视频提出问题，实际能力取决于所用模型 | 语言解释容易获得，持续记录和可信计算更有产品价值 | 稳定的分段指标、可比较历史条件、来源明确的长期反馈 |

**需要成立的产品差异是：用户能用它看清自己的长期变化，并将反馈落实到下一次训练。** 如果最终只有骨架覆盖和泛化点评，竞争力仍然不足。

## 六、创新点及其实现依据

### 1. 将训练量与动作表现放到同一条时间线上

每段视频关联组次、重量、动作变式、拍摄条件和用户备注。系统区分“不同负重下的表现”和“同等条件下的变化”，避免直接混合排名。

### 2. 可回放、可纠正的分析结论

输出由“观察结果、证据片段、适用条件、建议关注点”组成。用户或教练可以修正动作分段、计数和解释，修正内容保留版本，供后续对比使用。

### 3. 对比用户自身的可比历史

优先比较同一动作变式和相近机位，按重复动作阶段进行对齐。拍摄条件不足时说明无法比较的部分。个人基线用于观察变化，不自动代表动作正确或适合继续增加训练负荷。

### 4. 把拍摄可靠性作为分析输入

关键点遮挡、人物出框或视角差异会影响结果。系统先检查可分析性，再决定输出哪些指标，并显示数据覆盖范围；不能把模型原始置信度直接包装成经过校准的“正确概率”。

## 七、技术路线与 AI 的职责*

| 层次 | 候选技术 | 主要职责与注意事项 |
|---|---|---|
| Web | React、TypeScript、视频播放器、Canvas／SVG、图表组件 | 视频时间线、关键点叠加、并排回放和报告 |
| Android | Kotlin、Jetpack Compose、CameraX、Media3 | 拍摄、上传、训练记录及回放；与 Web 共享分析结果结构 |
| 服务端 | FastAPI、Pydantic、SQLAlchemy、PostgreSQL | 用户与权限、训练记录、视频元数据、分析任务和结果版本 |
| 视频处理 | FFmpeg、OpenCV | 方向与时间戳处理、抽帧、片段生成；统一处理可变帧率和旋转信息 |
| 姿态估计 | MediaPipe Pose Landmarker 等预训练方案 | 提取人体关键点；具体模型以目标设备和真实样例评估后选定 |
| 时序分析 | NumPy／SciPy、状态机、峰谷检测、阶段匹配 | 动作分段、时长与轨迹计算；规则随动作类型区分 |
| 语言解释 | 大语言模型、经过审核的动作说明与结构化输出 | 根据已有指标解释变化、组织反馈和处理追问 |
| 任务与存储 | 独立分析 worker、对象存储或私有文件存储 | 视频异步处理、进度反馈、访问控制与删除 |

[MediaPipe 官方文档](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker)说明其可处理图像和视频并输出人体关键点。这为姿态分析提供技术基础，但关键点输出并不等于训练质量评定。

几何指标与时长由程序计算，模型负责解释。单目视频中的深度与世界坐标具有估计误差，不能直接当作精确的真实关节角度、受力数据或医学测量。运动类型、适用视角和评价规则需要由专业人员参与审核。

可复用现有项目的 Web、FastAPI、Android 通用工程结构；训练业务、鉴权、视频任务与算法仍需专门设计。核心数据包括用户、动作定义、训练计划、训练组、视频、拍摄条件、分析版本、人工修正和关注点。

## 八、实现难易程度与可行性

| 能力 | 难度 | 难点来源 | 可行路径 |
|---|---|---|---|
| 训练日志与计划 | 较低至中等 | 输入便利性、跨端同步 | 复用历史数据，减少重复填写 |
| 视频上传和回放 | 中等 | 大文件、失败恢复、编解码差异 | 限定受支持格式、异步转码并保留原始时间关联 |
| 人体关键点叠加 | 中等 | 光照、遮挡、机型与模型性能 | 先用真实手机视频评估模型，再确定处理位置 |
| 重复计数与阶段切分 | 中高 | 动作变式、不完整动作与停顿 | 按动作定义规则，允许人工纠正 |
| 历史动作对齐 | 较高 | 节奏不同、机位不一致、关键点缺失 | 分阶段匹配并设置比较条件 |
| 可靠的动作反馈 | 高 | 个体差异、标注分歧、解释容易过度推断 | 专业审核、只输出可支持的观察、显式保留不确定项 |
| 个性化训练衔接 | 高 | 负荷安排与恢复信息复杂 | 先提供可编辑关注点和审核过的安排规则，逐步积累评估依据 |

**技术可行性：**现成姿态模型降低了基础识别门槛，完整视频复盘流程具备工程实现路径。核心难题是从检测结果得到稳定、有意义的反馈，而非接入模型 API。

**数据可行性：**需要获得授权、覆盖不同体型、衣着、机位与动作节奏的样例；同一视频最好由两名相关专业人员独立标注并处理分歧。公开数据的使用须核对许可，不能只挑选效果好的演示样例。

**团队可行性：**A 可负责 Web 复盘与公共接口，B 负责日志、数据库及任务管理，C 负责视频和时序分析，D 负责移动采集及联合测试。关键外部依赖是运动专业审核和真实使用者，职责建议不等于已经具备这些资源。

**成本可行性：**主要成本来自视频存储、转码与推理。应按视频时长、分辨率、抽帧频率、并发量和保存期限估算；不能仅依据一次模型调用价格判断。端侧与服务端处理需要结合设备兼容性和使用体验选择。

## 九、实用性、使用频率与推广

训练日志是经常使用的入口，视频用于用户关注的训练组，历史对比为连续使用提供理由。产品应支持“只记日志”“只分析一组”“完整复盘”等不同投入程度，避免要求每次训练都全程录像。

较合适的初始推广场景是校园健身社团与教练带领的小规模训练群体。用户可以先体验自己的两次训练对比，再决定是否长期记录。商业化可探索基础日志免费、历史视频容量与深度对比付费、教练协作服务等方式，付费意愿需要验证。

体育空间的拍摄限制、旁人入镜、视频隐私和上传负担会影响真实使用。默认私有、按需分享、人物遮挡处理与明确删除机制属于产品设计的一部分。

## 十、效果验证与选题判断

以下是拟验证指标，不是已完成的实验结果：

| 验证目标 | 方法 | 重点指标 |
|---|---|---|
| 分析是否可靠 | 与专业人员标注比较，按动作与拍摄条件分组 | 计数误差、阶段定位误差、错误反馈率、无法分析比例 |
| 对比是否有意义 | 同一人的相近条件历史视频与不同机位视频分别测试 | 对齐成功率、错误比较率、人工修正量 |
| 反馈是否更有用 | 对比普通相册回看、泛化点评与证据化复盘 | 找到问题所需时间、理解率、建议采纳率 |
| 是否愿意持续使用 | 真实训练试用并记录放弃原因 | 拍摄完成率、记录耗时、重复使用情况 |

不把短期试用中的体重、增肌或伤病变化作为产品已有效的证据。若拍摄负担大于用户收益，或专业审核发现错误反馈频繁，应优先调整产品入口和分析边界。

**选题判断：**需求具有持续性，影像展示直观，具备算法与产品结合空间；技术不确定性较高。最值得投入验证的部分是“条件可比的个人历史复盘”和“反馈能否真正被用户采用”。
