# PuppleTrouble 项目协作

本规范适用于 A Web 前端、B 后端兼数据库、C 后端兼算法、D Android 移动端。默认分支为 main，远程为 origin。日程见[项目开发计划](项目开发计划.md)，模块与评审责任见[分工安排](分工安排.md)。

## 1 分支约定

main 保存可验收的集成结果，通过 Pull Request 合入；不要把未完成工作直接推到 main。每项任务建短期分支，完成后合并并删除远端任务分支（先确认已合并）。

| 前缀 | 用途 | 示例 |
|---|---|---|
| feat/ | 新增用户功能或 API | feat/web-palette-editor |
| fix/ | 修复缺陷 | fix/api-color-lock |
| docs/ | 说明、计划与契约 | docs/startup-guide |
| refactor/ | 保持行为的结构调整 | refactor/algorithm-extraction |
| test/ | 增补或调整测试 | test/android-project-restore |
| chore/ | 工程配置、工具、依赖维护 | chore/python-dependencies |

分支通常由一人负责。若共同维护同一分支，合并远程分支，避免 rebase 改写已共享历史。大功能拆成可验收的小变更，不能长期积攒到末期才联调。

## 2 提交消息规范

格式为 `type(scope): 简洁说明`，scope 可省略。标题说明实际变化，建议不超过 72 字符；必要时空一行补充原因、影响、验证和关联任务。单次提交只围绕一类目的，不使用“update”“修改一下”等无法判断内容的主题。

| type | 何时使用 | 示例 |
|---|---|---|
| feat | 新功能或新增可用能力 | feat(web): 增加配色候选并排预览 |
| fix | 修复已有错误行为 | fix(api): 拒绝修改锁定颜色 |
| docs | 文档变更 | docs: 补充项目启动方式 |
| refactor | 重构且不改变对外行为 | refactor(algorithm): 拆分颜色采样与蒙版计算 |
| perf | 可验证的性能优化 | perf(web): 复用高亮蒙版减少重复绘制 |
| test | 测试代码和测试样例 | test(api): 覆盖项目版本冲突 |
| style | 代码格式、缩进等无行为变化 | style(android): 统一 Kotlin 格式 |
| build | 构建系统、依赖和打包配置 | build(web): 固定构建依赖版本 |
| ci | 自动检查、发布流水线 | ci: 增加后端测试检查 |
| chore | 其余维护 | chore: 更新忽略规则 |
| revert | 撤销一个已有提交 | revert: 撤销错误的配色策略更新 |

`style` 不表示页面配色、布局等用户可见改动，后者通常属于 feat 或 fix。对外不兼容的接口修改使用 `feat(api)!: ...` 等形式，并在正文写 `BREAKING CHANGE: ...`，同时更新接口文档、双方模型及迁移说明。

## 3 开始工作前拉取

首先确认工作目录干净。以下命令从仓库根目录执行：

```powershell
git status
git switch main
git pull --ff-only origin main
git switch -c feat/web-palette-editor
```

示例分支名换成当前任务。`--ff-only` 失败说明分支已分叉，应查看差异后处理，不能用 reset 或强推抹掉提交。如果有未提交内容，先在原任务分支整理提交；不在未知脏状态下切换 main、直接 pull 或自动 stash 他人的修改。

## 4 提交和推送前同步

“提交前拉取”以不丢失当前工作为前提：工作开始时先拉取；工作中用 fetch 检查更新。如果当前有修改，先完成本地提交，再合并最新 main，验证后推送。

```powershell
git status
git fetch origin
git diff
git diff --check
git add frontend/src
git diff --cached
git diff --cached --check
git commit -m "feat(web): 增加配色候选并排预览"
git merge origin/main
```

`git add` 的路径换成实际修改文件，逐项检查 staged diff，避免顺手加入密钥、真实用户素材或无关变更。合并后重新执行受影响检查。没有远程更新时 merge 不会引入额外变更。

```powershell
git status
git push -u origin HEAD
```

若推送被拒绝，先检查同名远端任务分支。确认在本任务分支且本地已提交后，使用 `git pull --no-rebase origin <当前任务分支名>` 合并协作者更新，再验证与推送。尖括号是占位说明，不可原样粘贴。

不执行 `git push --force`。已发布的错误用修复提交或 `git revert <提交号>` 处理；revert 涉及共享逻辑时先沟通。不要在 main 上 rebase 共享历史。

## 5 冲突处理

1. 使用 `git status` 找出冲突文件，并查看双方意图。
2. 与对应负责人确认内容；接口、schema 和数据库迁移尤其不能机械选择一边。
3. 编辑合并结果，删除冲突标记，再用 `git diff` 检查。
4. `git add <已解决文件>` 后完成 `git commit`，并运行相关验证。
5. 若决定退出当前合并，确认后使用 `git merge --abort`，保留并重新检查工作区状态。

不要通过删除文件、强制覆盖或编造测试结果“解决”冲突。

## 6 PR 和 main 更新

PR 描述写清问题、最终行为、涉及模块、实际验证和剩余限制。界面附前后截图，接口附请求响应和失败示例。至少一位对应成员评审；流程见分工安排。

合并后，每位成员在完成当前本地工作后切回 main，执行 `git pull --ff-only origin main`，再从最新 main 开下一个分支。仅删除确认已合并且不再使用的分支。

## 7 验证和文档同步

文档变更检查链接、命令路径、JSON 示例、日期和 `git diff --check`。代码建立后，Web 检查类型／构建、单元和关键端到端；后端检查接口、权限、迁移和算法；移动端检查构建、状态与真机流程。尚未执行的检查标明未执行，文档校验不代表应用测试通过。

B 维护接口与数据库；C 维护算法与模型约束；A/D 更新两端模型。变更颜色角色、版本规则、配置或启动命令时同步对应文档。约束不只留在聊天中。

## 8 数据、密钥与 AI 编程

提交 `.env.example`，不提交 `.env`、API key、令牌、签名文件、私人图片与未授权素材。依赖锁文件和 Wrapper 应提交，环境、缓存和生成产物不提交。已泄露秘密要轮换，不能只加 ignore。

保存关键 AI 提示、模型、日期、人工修改与验证记录，去除私密数据后用于可选参赛材料。生成代码必须理解并审查，mock 必须标识；计划、完成和验证结果分开记录。

项目名称固定为 PuppleTrouble／玩犊紫。UTF-8、LF 换行。没有团队决定前，不擅自新增源码开源许可证。评审材料另做匿名副本。
