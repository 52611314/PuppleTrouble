# 选机有数

> 贯穿二手数码设备选购、信息核实与到手验机的 AI 决策助手。

**提案状态：备选项目，尚未立项。** 本文分析产品需求、竞争差异与实现可行性，不代表已有检测能力或用户调研结论。竞品资料查阅日期：2026 年 11 月 12 日。

## 一、项目定位

选机有数面向预算有限、缺少设备知识的普通消费者，以二手笔记本为优先切入品类，将用户用途、商品描述、配置资料、沟通记录与验机结果组织为一份可以持续更新的购买档案。

核心价值是：**让用户知道自己为什么考虑某台设备、还缺哪些信息，以及收到设备后应该如何核对。** 购买建议应能够指向来源，待核实信息应转化为具体问题，验机结果应回到原始需求和卖家承诺中进行比较。

“选机有数”表达的是选购有依据、比较有条理、验机有步骤。项目属于 AI＋生活方向；手机适合收集商品截图、沟通材料和现场检查，Web 适合多商品比较、报告查看与档案管理。

## 二、目标用户与需求场景

| 用户 | 典型场景 | 实际需求 |
|---|---|---|
| 预算有限的大学生 | 购买满足课程软件、编程或基础剪辑要求的二手电脑 | 把用途转成配置需求，避免只看价格和处理器名称 |
| 缺少数码知识的普通消费者 | 面对同系列不同年份、配置和成色的商品 | 对齐配置，理解取舍和信息缺口 |
| 首次线下交易或收货验机者 | 没有完整检查经验，又担心遗漏重要项目 | 获得与这台设备相关的分步检查流程 |
| 帮家人、同学选设备的人 | 同时比较多个候选并解释推荐理由 | 保存信息和依据，便于共同确认与后续复查 |

购买频率较低，但用户在购买前后会集中投入时间。产品是否成立，应看单次决策帮助和完整流程使用情况，而不是单纯追求每日活跃。

## 三、需要解决的痛点

### 1. 用途很具体，商品参数却难以理解

“上课记笔记、运行开发工具、偶尔剪辑视频”是用户的自然表达。内存、处理器、显卡、屏幕和续航之间的取舍，往往无法从一个综合跑分或“适合大学生”的描述中得到答案。

### 2. 商品信息不完整且口径混杂

同一系列可能包含不同处理器、屏幕、内存和接口组合。“高配”“几乎全新”“电池很好”等描述不能直接变成结构化事实。图片、标题和聊天记录之间也可能存在歧义，需要补问才能确认。

### 3. 比较之后，用户仍不知道该问什么

普通参数表能够列出差异，却不一定指出“现在缺少哪条信息，补充后是否可能改变选择”。用户容易在无关参数上花费时间，却忽略自己需要的接口、实际配置或电池报告。

### 4. 到手检查与购买理由脱节

通用验机清单较长，用户不知道哪些项目最重要，也不知道测试结果意味着什么。商品描述、沟通承诺、系统报告和手动检查结果分散，后续很难重新核对。

## 四、完整使用流程

**描述用途与预算 → 导入候选商品 → 确认配置与来源 → 对照需求比较 → 补问关键问题 → 生成设备检查任务 → 导入报告与手动结果 → 汇总差异并保存档案。**

### 使用示例

用户准备购买用于编程和日常学习的二手笔记本，导入三份商品截图。系统整理处理器、内存、硬盘、屏幕、重量、报价等字段，对缺失值保留空缺，并让用户确认识别结果。

用户声明需要连接两台外接显示器。系统发现其中一台的接口能力尚未确认，生成针对性提问；另一台内存信息只出现在卖家聊天中，尚无报告支持。用户补充资料后，比较结果随证据变化更新。

收货后，用户按设备档案核对配置，导入系统报告，并完成屏幕、键盘、接口、摄像头等交互检查。最终档案显示“与描述一致”“存在差异”“尚未检查”的项目及其依据，而不是直接给出“绝对可靠”的结论。

## 五、功能结构与产品价值

| 模块 | 主要功能 | 对用户的价值 |
|---|---|---|
| 用途建模 | 预算、目标软件、携带要求、屏幕偏好、必需接口及可接受取舍 | 将自然语言转成可确认的硬性条件和偏好 |
| 商品采集 | 截图、文本、配置图片、沟通材料导入及结构化确认 | 降低整理成本，保留原始来源 |
| 配置对齐 | 型号别名、年份、处理器完整型号、内存与存储、屏幕选件区分 | 避免混淆不同配置和系列名称 |
| 候选比较 | 硬性条件筛选、取舍解释、信息完整度、候选更新 | 让推荐与用户用途对应 |
| 补问助手 | 按影响决策程度整理待核实问题，支持补充回答 | 用较少的问题补齐关键证据 |
| 验机任务 | 根据设备类型、用户用途和卖家承诺生成步骤 | 避免只有冗长的通用清单 |
| 报告解读 | 导入系统报告，提取字段，解释缺失和矛盾项 | 降低阅读检测信息的门槛 |
| 交互检查 | 屏幕色块、键盘按键、音视频设备与人工接口记录等 | 将检查过程拆成可执行的小任务 |
| 设备档案 | 商品原文、材料版本、用户确认、检测时间、结果与分享导出 | 便于共同选购、收货核对及后续维护 |

“合理价位”可作为后续研究能力，必须标明样本来源、时间、成色和配置口径。挂牌价与成交价有区别，缺少可靠成交数据时不能伪造市场估值或保值率。

## 七、创新点与可信机制

### 1. 字段级证据状态

每个重要字段保存值、来源位置、采集时间、适用设备、确认状态和冲突记录。例如“16GB 内存”可以来自商品标题、卖家回答或设备报告，三者支持力度不同；用户确认识别正确，也不代表信息已被独立验证。

状态可包括“卖家描述”“用户转录”“报告支持”“用户手动检查”“待核实”“来源冲突”。不宜简单压成一个置信分数，更不能把模型自评当成真实可信度。

### 2. 按决策影响组织补问

系统首先检查用户的硬性条件。如果接口是否支持某种连接方式会直接影响使用，就优先询问；与用户用途关系较小的外观信息可以后置。信息补齐后，系统说明比较结论为何改变。

### 3. 从商品承诺生成验机任务

卖家宣称的配置、设备功能和用户必需能力分别关联到检查项。每项显示检查方法、输入材料、适用条件和结果解释；记录“未完成”与“失败”两种不同状态。

### 4. 对不同类型的结论采用不同计算方式

配置匹配和报告数值由规则处理；型号资料从可追溯知识库查询；语言模型整理需求和解释取舍。系统可以指出证据冲突，但不能仅凭冲突判定欺诈、拆修或假货。

### 5. 比较过程可追溯

保存不同候选、报价、资料及用户需求的版本。新增证据后展示变化，避免用户不知道推荐是依据哪一次商品描述得出的。

## 八、技术路线与实现难点

| 层次 | 候选技术 | 主要职责 |
|---|---|---|
| Web | React、TypeScript、结构化表单、对比表、证据查看器 | 多候选比较、材料定位、报告阅读与档案分享 |
| Android | Kotlin、Jetpack Compose、拍照与系统分享接收 | 截图采集、现场核对与分步检查 |
| 服务端 | FastAPI、Pydantic、SQLAlchemy、PostgreSQL | 用户与权限、商品和设备档案、证据版本、比较与检查任务 |
| OCR 与多模态 | PaddleOCR 等 OCR、可配置视觉语言模型 | 识别截图字段和来源区域；保留原图供确认 |
| 型号与配置知识 | 人工整理的结构化资料、全文检索；语义检索按需求引入 | 处理型号别名、资料来源和配置选件；精确字段仍按结构查询 |
| 比较规则 | 硬性约束、偏好权重、字段冲突与缺失规则 | 生成可解释的候选取舍，不混合性能与未知成色 |
| 报告处理 | HTML／JSON／文本解析器、格式适配与字段校验 | 提取报告信息，保留生成时间及设备关联信息 |
| AI 解释 | 大语言模型、检索资料、结构化输出 | 需求澄清、补问组织、报告解释与交互引导 |
| 检查页面 | 浏览器交互测试与人工确认 | 展示屏幕测试画面、按键反馈等；受设备及权限限制的项目明确说明 |

[Microsoft 官方文档](https://support.microsoft.com/en-us/windows/experience/power-battery/caring-for-your-battery-in-windows)提供 Windows 电池报告的获取方法，可作为报告导入的一种依据。满充容量与设计容量的比值可以帮助理解报告数据，但不能据此保证实际续航、未来寿命或报告真实性。

普通浏览器不能可靠读取完整硬件、硬盘健康、拆修历史和全部接口能力。需要的深层信息通过用户导入系统／厂商报告、人工检查或后续专用工具取得；网页测试也不能证明设备在所有条件下正常。导入 HTML 报告时只解析数据，不执行其中的脚本。

核心数据包括用途档案、候选商品、配置字段、证据材料、来源关系、需求版本、比较结果、补问记录、检查模板、检测结果和设备档案。现有通用三端框架可以复用，商品与验机业务需独立建设。

## 九、实现难易程度与可行性

| 能力 | 难度 | 关键问题 | 可行路径 |
|---|---|---|---|
| 档案与比较界面 | 中等 | 多来源材料组织、跨端更新 | 统一字段模型，采用证据定位与版本管理 |
| 截图信息提取 | 中高 | 文字模糊、配置缩写、同图多商品 | OCR 与模型互补，重要字段人工确认 |
| 精确型号匹配 | 高 | 系列重名、不同配置选件、资料不全 | 从可审核型号资料建立结构化库，歧义时继续询问 |
| 用途匹配 | 中高 | “能用”取决于具体软件版本和工作负载 | 将硬性条件与偏好分开，明确推荐适用情境 |
| 报告解析 | 中高 | 不同格式、缺失字段、截断或修改材料 | 格式适配、完整性提示、保留来源，不宣称防伪认证 |
| 检查流程生成 | 中等 | 项目繁多、用户理解门槛 | 经人工审核的规则模板与通俗说明 |
| 市场价格判断 | 高 | 成交数据不足、成色差异、更新频繁 | 有可靠样本再评估，公开样本口径及时间 |
| 设备真伪与隐藏故障判断 | 很高 | 材料有限、远程不可观测 | 提供待查事项与转专业检测路径，不输出无依据保证 |

**技术可行性：**OCR、文档解析、规则比较和结构化问答都有成熟基础，完整流程具有实现路径。最值得投入的技术资产是型号知识、证据关联和验机规则，而不是单独训练一个“懂电脑”的聊天模型。

**数据可行性：**可从厂商规格页、系统官方说明、用户授权材料和团队实测建立资料。商品页面与报告包含个人信息，应支持遮挡或删除；序列号等身份字段按需要最小化保存。用户主动导入可减少对平台接口和页面结构的依赖，后续采集能力再单独核对授权与使用条件。

**团队可行性：**A 可负责比较界面与公共接口，B 负责证据档案、数据库和任务服务，C 负责信息提取、型号匹配与解释，D 负责移动采集与检查流程测试。需要熟悉数码设备的人审核内容，并提供不同机型和异常报告样例。

**成本可行性：**主要来自视觉模型、资料维护与材料存储。OCR 和规则可承担重复处理，模型用于语义整理与解释。价格情报、硬件覆盖与资料更新需要持续人力，不应只计算接口费用。

## 十、实用性与产品发展空间

用户收益应体现在更快筛掉明显不适合的候选、少漏问关键问题、提高检查完成率、降低沟通成本。可用价值不等于保证交易成功，也不等于能发现全部隐藏故障。

产品可在购买前、沟通中和收货时多次使用；购后档案可用于维护、升级或转卖，但这些能力应围绕同一设备资料自然延伸。笔记本以外的手机、相机可以扩展，前提是分别建设型号知识、检查方法与验证样例。

初始推广可面向校园二手交易群体与帮助同学选机的人。商业化可探索单次完整选购档案、协作服务、专业检测转介或维修机构工具。若存在商业推荐关系，应公开展示，避免影响候选排序和用户信任。

主要阻力包括：用户只愿意免费问一次、卖家不配合补充信息、型号资料维护昂贵，以及用户把辅助分析误当成质检担保。是否愿意分享材料、完成检查和为完整流程付费，都需要验证。

## 十一、效果验证与选题判断

以下为拟验证方法，不是已取得的效果：

| 验证目标 | 方法 | 重点指标 |
|---|---|---|
| 字段提取是否准确 | 建立人工核对的授权商品样例，包含模糊图、缺失和冲突 | 核心字段准确率、错误补全率、型号歧义识别率 |
| 比较是否有帮助 | 对比人工整理、通用 AI 问答与本系统完成相同任务 | 整理时间、关键遗漏、用户能否复述推荐依据 |
| 补问是否有效 | 由熟悉设备者审核问题，观察用户实际沟通 | 关键缺口覆盖率、有效回复率、重复问题数 |
| 检查是否容易完成 | 在已知状态的设备上执行流程 | 完成率、平均耗时、步骤误解、问题发现及误报 |
| 证据是否可追溯 | 随机抽取结论要求回到原始来源 | 来源定位成功率、错误设备关联、更新后的状态一致性 |

不能将模型推荐的一致性当成选购正确率，也不能将用户“觉得放心”直接作为故障识别效果。若资料经常不足、需要大量人工补全，或相比普通清单没有明显收益，应重新调整入口和知识覆盖。

**选题判断：**需求触发明确，用户容易理解购买前后的价值；技术展示可围绕多模态材料、证据状态和动态检查流程展开。主要不确定性是信息质量与知识维护，基础工程可行性较强。与“练有据”相比，影像算法依赖较低，结构化信息处理与规则建设更重。
