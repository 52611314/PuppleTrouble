# PuppleTrouble 项目协作

适用于 A（Web，兼架构／后端框架）、B（后端／数据库）、C（后端／算法）、D（Android，兼六天联合测试）。默认分支 main，远程 origin。日程见[项目开发计划](项目开发计划.md)，职责见[分工安排](分工安排.md)。命令默认从仓库根目录执行。

## 1 必须执行的 HANDOFF 交接

统一交接入口为 [docs/HANDOFF.md](HANDOFF.md)。**当前处于工程初始化阶段，按队长要求该文件留空，暂不填写；以下更新规则在恢复交接记录后执行。期间在提交／PR 和对应模块文档记录实际变化，不往空文件补标题或模板。****任何成员修改代码、配置或其他文档前，先同步并阅读 HANDOFF；修改后更新 HANDOFF，与对应变更一起提交。** 仅阅读不要求制造一条交接修改。

1. 开工前：在干净工作区拉取最新 main，先读 HANDOFF，确认实际状态、接口约定、未完事项及接手任务，再改其他文件。
2. 计划涉及他人模块或共享框架时：在本任务分支的 HANDOFF 中记明范围、主责和依赖，与负责人对齐；分支内记录不会自动通知其他成员，必要时直接沟通，不能据此认为文件已被独占。
3. 改动结束、提交之前：更新“当前真实状态／下一步”，追加日期、成员、分支或 PR、变更文件、接口配置影响、实际验证、限制、下一接手人和具体动作。未实现、未验证分别标注；日志去敏。
4. 合并他人更新后：重读 HANDOFF，保留双方有效记录，按合并后的事实整理共享状态；如需修改，再更新验证结果并提交。HANDOFF 与功能／文档同时交付，不等下一轮再补。
5. 接手时：从下一步任务和链接复跑必要检查，确认输入输出及阻塞后继续。周期末和 D 的六天测试均将结果或报告链接写入 HANDOFF。

HANDOFF 是交接摘要，不替代接口、计划或测试报告；详细约定改原文档，再在交接中附链接。禁止记录密钥、令牌、私人素材和敏感日志。

## 2 分支约定

main 保存可验收的集成结果，日常功能通过 Pull Request 合入。每项任务建短期分支，大功能拆成可验收变更，不长期积攒到末期联调。

| 前缀 | 用途 | 示例 |
|---|---|---|
| feat/ | 新增用户功能或 API | feat/web-palette-editor |
| fix/ | 修复缺陷 | fix/api-color-lock |
| docs/ | 说明、计划与契约 | docs/cycle-plan |
| refactor/ | 保持行为的结构调整 | refactor/algorithm-extraction |
| test/ | 增补或调整测试 | test/android-project-restore |
| chore/ | 工程配置、工具、依赖维护 | chore/python-dependencies |

分支名可使用英文标识。分支通常由一人负责，共同维护时合并远程分支，避免 rebase 改写共享历史。仅删除确认已合并且不再使用的任务分支。

## 3 提交类型与简体中文描述

**类型保留英文，其余人为撰写的描述使用简体中文。** 统一标题格式为 `type:简体中文描述`，可选中文范围为 `type(中文范围):简体中文描述`，例如 `docs:新增项目启动文档`。正文的原因、影响、验证说明也用简体中文；Git 命令、文件路径、库名、API 标识等保留原名。范围不用 web/api/android 等英文词代替中文。

标题说明具体变化，建议不超过 72 字符。单次提交只围绕一个目的；必要时空一行补原因、验证、关联任务和限制。不使用“update”“修改一下”等无法判断内容的主题。

| type | 何时使用 | 示例 |
|---|---|---|
| feat | 新功能或新增可用能力 | feat(前端):新增配色候选并排预览 |
| fix | 修复已有错误行为 | fix(接口):拒绝修改锁定颜色 |
| docs | 文档变更 | docs:新增项目启动文档 |
| refactor | 重构且不改变对外行为 | refactor(算法):拆分采样与蒙版计算 |
| perf | 有验证证据的性能优化 | perf(前端):复用高亮蒙版减少重复绘制 |
| test | 测试代码和样例 | test(接口):补充项目版本冲突用例 |
| style | 格式、缩进等无行为变化 | style(移动端):统一代码缩进 |
| build | 构建、依赖和打包配置 | build(前端):固定构建依赖版本 |
| ci | 自动检查和发布流水线 | ci:新增后端测试检查 |
| chore | 其余维护 | chore:更新忽略规则 |
| revert | 撤销已有提交 | revert:撤销错误的配色策略更新 |

`style` 不表示页面配色／布局改动，用户可见的改变通常属于 feat 或 fix。不兼容接口修改示例为 `feat(接口)!:调整配色角色字段结构`；正文用标准标记 `BREAKING CHANGE:配色角色字段结构已调整，旧客户端需同步迁移`，标记保留、说明中文，并更新接口、客户端模型与迁移说明。

Git 自动生成的 merge/revert 标题也应编辑为上述格式，例如 `chore:合并主分支最新更新`。本规范用于后续提交，不改写已有共享历史。

## 4 开始工作前拉取并阅读交接

先确认工作区干净，再执行：

```powershell
git status
git switch main
git pull --ff-only origin main
Get-Content -LiteralPath docs/HANDOFF.md -Encoding UTF8
git switch -c feat/web-palette-editor
```

分支名换为当前任务。`--ff-only` 失败说明分支分叉，应查看差异处理，不用 reset 或强推抹掉提交。有未提交内容时，先在原任务分支整理提交；不在未知脏状态切 main、直接 pull 或自动 stash 他人的改动。

## 5 提交和推送前同步

“提交前拉取”以不丢失工作为前提：开工先 pull；工作中 fetch 查看更新。存在修改时，先更新 HANDOFF、完成本地提交，再合并最新 main 并验证，最后推送。

```powershell
git status
git fetch origin
git diff
git diff --check
git add frontend/src docs/HANDOFF.md
git diff --cached
git diff --cached --check
git commit -m "feat(前端):新增配色候选并排预览"
git merge --no-commit origin/main
```

`git add` 路径换为实际修改，逐项检查暂存差异，不捎带秘密或无关变更。`--no-commit` 在产生合并提交时停下供核对；可快进或已同步时不会停下。发生冲突按下一节处理。

合并后重读 HANDOFF，重新执行受影响检查；若合并仍未提交，连同交接调整以 `git commit -m "chore:合并主分支更新并核对交接"` 完成合并。如已快进且又修改了交接，单独提交实际交接变化；没有变化不制造空提交。

```powershell
Get-Content -LiteralPath docs/HANDOFF.md -Encoding UTF8
git status
git push -u origin HEAD
```

推送被拒绝时先看同名远程任务分支；确认处于本任务分支且工作已提交后，`git fetch origin`，再以 `git merge --no-commit origin/<当前任务分支名>` 合并协作者更新，按上述流程核对交接、验证并用中文标题提交，再推送。尖括号为占位说明，不可照抄。不使用 `git push --force`，不在 main 上 rebase 共享历史；已发布错误用修复提交，或沟通后使用 revert 并编辑中文消息。

## 6 冲突处理

1. `git status` 找冲突，结合 HANDOFF 查看双方意图；架构／契约找 A/B、业务／迁移找 B、算法找 C、移动／测试找 D。
2. 接口、schema 和迁移不能机械选一边；HANDOFF 保留双方有效交接记录，按真实合并结果更新状态与接手人。
3. 去掉冲突标记，检查 diff，运行受影响验证，暂存已解决文件和 HANDOFF 后，用简体中文消息完成提交。
4. 如决定退出当前合并，确认后 `git merge --abort`，保留并重查工作区。

不通过删除文件、强行覆盖或编造结果解决冲突。

## 7 PR、验证和文档同步

PR 写清问题、最终行为、涉及模块、实际验证和限制；界面附截图，接口附请求响应与失败样例。至少一位对应成员评审，检查 HANDOFF 是否随变更更新。合并后完成当前本地工作，再回 main 拉取并重读交接，开下一任务分支。

文档变更检查链接、命令路径、JSON、日期及 `git diff --check`。代码建立后，Web 检查类型／构建及关键交互；后端检查接口、权限、迁移和算法；移动检查构建、状态及真机。未执行须注明，文档校验不等于应用测试通过。

A 维护架构与公共框架并牵头接口设计，B 维护业务 API／数据库和契约发布一致性，C 维护算法／模型约束，A/D 更新两端模型。颜色角色、版本、配置或启动命令变化须同步对应文档及 HANDOFF。

各模块日常自测由本人负责；D 在 D6、D12、D18、D24、D30 组织联合测试，汇总清单、缺陷和复测，各成员修复自己模块。每个 Sprint 的前／后三天节点核对成果，不重复开一轮由 D 汇总的专项测试。

## 8 数据、密钥与 AI 编程

提交 `.env.example`，不提交 `.env`、API key、令牌、签名文件、私人图片或未授权素材。锁文件和 Wrapper 应提交，缓存与生成产物不提交。泄露的秘密需轮换，不能只加 ignore。

保存去敏后的关键 AI 提示、模型、日期、人工修改及验证记录；生成代码必须理解和审查，mock 明示，计划、完成和验证分开记录。

项目名固定为 PuppleTrouble／玩犊紫，UTF-8、LF 换行。未经团队决定不新增源码开源许可证；评审材料另做匿名副本。
